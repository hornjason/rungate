# AGENTS.md Template Spec

## Problem Statement

The AGENTS.md file is the single entry point for agents working in a project. It must be fully regenerated by scaffold on every run — no hand editing, no preserved sections. User-specific rules go in CLAUDE.md, not AGENTS.md.

The template was previously hardcoded in scaffold-project.ts, making it hard to update rules or change section order without editing TypeScript. This spec defines the architecture for separating template content from scan logic.

## Design Decisions

| # | Decision | Rationale |
|---|----------|-----------|
| D-1 | AGENTS.md is fully harness-owned — always regenerated | Spec line 24: "Everything is regenerable." User rules go in CLAUDE.md |
| D-2 | Universal rules in config/universal-rules.yaml, not hardcoded | Adding a rule should be editing a list, not TypeScript |
| D-3 | Template in prompts/agents-md-template.md with ${VAR} placeholders | Section order changes = editing markdown, not code |
| D-4 | Scaffold fills variables from project scan | Scan logic stays in scaffold-project.ts, template is data |
| D-5 | Under 16 rules — sigmoid collapse at 16 (arXiv 2608.02639) | Research-backed limit. Currently 8 rules |
| D-6 | Rules come from real failure patterns, not theory | Every rule traces to a specific audit finding or correction |
| D-7 | Governing Spec + Specs merged into single table | Council 2026-09-20: one table = one scan point, saves 8 lines, single sanitization path |
| D-8 | Governs authored LLM-once-then-static | LLM generates on first pass, human reviews, scaffold reads deterministically forever after. No LLM at scaffold time |
| D-9 | Content that doesn't match governs → new file | Prevents intent drift. Governs is a constraint, not just a description |
| D-10 | Split files group under one routing entry | Split pieces share parent intent. One entry covers N files: "Bootstrap phases (5 specs) → specs/bootstrap/" |
| D-11 | ~~Routing table shows non-obvious mappings only~~ **Superseded by D-11a (#617)** | Agent can find specs/BOOTSTRAP-PHASE-0.md by name. Routing table is for non-inferrable connections only (ETH Zurich) |
| D-11a | A low-information row beats silence: emit every document, mark the ones with nothing to say | D-11's instinct is right — `\| environments \| docs/ENVIRONMENTS.md \|` teaches nothing about *when* to read the file. Its action was wrong: dropping the row does not produce a better row, it produces no evidence the document exists. Measured on the asaCommandCenter consumer, **0 of 38 top-level `docs/*.md` carried a `governs:` field, so all 38 were dropped** — and a DA that never opened `docs/ENVIRONMENTS.md` filed a false P1 on production. A document with no `governs:` is UNMEASURED, not "governs nothing" (`.claude/rules/config-access.md`, *Silent Default Substitution*). Exclusion is now the document's own declaration — `status: archived` or `routing: exclude` — not a string-similarity accident |
| D-12 | Split-spec directory name derived from filename, no LLM | `BOOTSTRAP-DATA-FLOW-SPEC.md` → `specs/bootstrap-data-flow/`. Deterministic. Human already named the file well |
| D-13 | Routing table and create-table are the same list | Where to READ and where to WRITE should be mechanically linked. Same categories, two directions. One drifts = both drift |
| D-14 | Three-tier context architecture | Tier 1 (hot, unconditional): AGENTS.md + `.claude/rules/` without `paths:`. Tier 2 (specialist, path-scoped): `.claude/rules/` with `paths:` + agent briefs. Tier 3 (cold, on-demand): prompts/, specs/, CODE-MAP (arXiv 2602.20478) |
| D-15 | AGENTS.md capped at 100 lines | Sigmoid collapse (arXiv 2608.02639): follow rate drops 96%→20% at 16+ rules. AGENTS.md was 205 lines. Reference tables moved to `.claude/rules/` scoped files |
| D-16 | Scoped rules use `paths:` YAML list frontmatter | Claude Code spec: `paths:` with YAML list format, not `globs:` JSON array. `alwaysApply` is not recognized. Rules without `paths:` load unconditionally |
| D-17 | Shared agent principles in unconditional rule, not briefs | `${SHARED_RULES}` and `${PROJECT_IDENTITY}` removed from brief templates — agents inherit project rules automatically. Dedup: 526→427 brief lines (19% reduction) |
| D-18 | Osmani test on every generated line | "Can the agent find this by reading code? Delete it." (ETH Zurich ICLR 2026). Tests table, reference files table removed — agents discover via `bun test` and `ls` |

## Three Content Types

| Type | Source | On re-scaffold | How to update |
|------|--------|----------------|---------------|
| Template (universal) | config/universal-rules.yaml + prompts/agents-md-template.md | Always regenerated | Edit config or template file |
| Scanned (project-specific) | scaffold-project.ts reads project files | Always regenerated from current state | Change the project, re-scaffold |
| User rules | CLAUDE.md (not in AGENTS.md) | Never touched by scaffold | User edits CLAUDE.md directly |

## Universal Rules (current)

These trace to specific failures from auditing sessions. New rules require a failure citation.

1. **Verify before asserting** — try it, then report what actually happened
   - *From: 8-entry repeated pattern "behavioral correction — verify before assuming" (learning-review 2026-08-28)*
2. **Never report PASS with known gaps** — list every gap honestly
   - *From: SC-3 and SC-11 marked as "scaffold gap" todos instead of being fixed*
3. **Never fake, shortcut, or game test results** — if it fails, it fails
   - *From: faked COMP audit with manual text instead of real tool output (2026-09-20 session)*
4. **Run full test suite before reporting done**, not just your file
   - *From: fresh Marcus ran only his test file, not bun test (COMP-2 partial fail)*
5. **Show real tool output, not summaries** — the raw data is the evidence
   - *From: truncated audit results presented as complete (2026-09-20 session)*
6. **Read docs before writing code** — the routing table tells you where to look
   - *From: scaffold changes made without reading governing spec first (COMP-5 violation)*
7. **Be honest — disagree when the evidence says otherwise**, don't confirm to be agreeable
   - *From: "You don't always have to agree with me" correction (2026-09-20 session)*
8. **Fix the source, not the output** — if you're hand-editing generated files, fix the generator
   - *From: hand-editing AGENTS.md all session instead of fixing the template (2026-09-20 session)*

## Adding a New Rule

1. Identify the failure — what went wrong, when, how was it caught
2. Write the rule — one line, action-oriented, specific
3. Add to config/universal-rules.yaml with failure citation
4. Re-scaffold — rule appears in every project's AGENTS.md
5. Verify via fresh agent test — does the rule change behavior?

Rules without a failure citation don't get added. "Seems like a good idea" is not evidence.

## Intent-Based Routing

The AGENTS.md Governing Spec Routing table must route by INTENT ("I want to test fixtures") not work area ("scaffold work"). The scaffold generates this automatically:

1. Spec template prompts author to write intent-based `governs:` at creation time (one-time, LLM-assisted)
2. `governs:` uses "I want to..." language — specific, stable, written once
3. Scaffold reads `governs:` from frontmatter — deterministic, no LLM at scaffold time
4. AGENTS.md routing table rebuilt from all `governs:` fields on every scaffold run
5. Same frontmatter → same routing → idempotent

**No LLM at scaffold time.** The intent is authored once when the spec is created. The scaffold just reads it mechanically. No non-determinism, no drift, no rewrites.

**Large files:** Files with multiple intents (like BOOTSTRAP-DATA-FLOW-SPEC.md with 5 phases) should be split into single-intent files — each under 500 lines, each with its own `governs:`. One file = one intent = one routing entry. A fresh agent couldn't even read 50% of the 2600-line bootstrap spec.

**Spec template:** `specs/SPEC-TEMPLATE.md` has the `governs:` field with guidance: "intent — 'I want to...' language. This drives the AGENTS.md routing table. Write once, be specific."

## Future: Cross-Tool Support (SC-254)

CLAUDE.md is Claude Code specific. For Cursor, Codex, Copilot — user rules need a tool-agnostic file. Proposed: PROJECT-RULES.md at repo root, referenced from AGENTS.md. Each tool's config file (@-includes, .cursor/rules, etc.) points to it.

### The command table published commands nobody could run (#363)

Every project rungate scaffolds got this table, and three of its rows had
never worked for anyone:

```
| Create spec | `bunx rungate create-spec "title"` |
| Create SC   | `bunx rungate create-sc --pattern <name> --params '<json>'` |
| Re-scaffold | `bun ~/Projects/rungate/scripts/scaffold-project.ts .` |
```

`package.json` declared **no `bin`**, so neither `bunx` form could run from
source or from the registry. The third row was one laptop's absolute path,
written into every consumer's AGENTS.md. The generator already had the "only
advertise a command that exists" discipline — applied to `convert-spec`, the
type check (#65/#76) and the clean-env row, one row at a time. These three
predate it.

**Three defects, each hiding behind the next.** With no `bin`, nobody got far
enough to notice that `scripts/create-spec.ts` and `scripts/create-sc.ts` were
not in `package.json`'s `files` either — so even a correct `bin` would have
shipped a dispatcher pointing at scripts the consumer never received.

The cost was not hypothetical. An agent reading AGENTS.md ran the command and
it failed. An agent reading package.json saw no `bin`, concluded rungate had
no CLI and was not distributable, and recommended hand-scaffolding a project.
Both readings of the repo were wrong, which is the state a single source
fixes: `lib/cli-commands.ts` is now the one place that says what dispatches,
and the manifest and the generator are checked against it.

Nothing in the repo stated that rungate is published to npm at all — the
`Repo:` line points at GitHub. For a consumer, distribution is the most
load-bearing fact there is, and it was the one fact nowhere in the tree. A
consumer's AGENTS.md now opens with an Install / Consume section; the
harness's own does not, because inside this repo `bunx rungate` resolves to
the PUBLISHED package and every command in rungate's own docs would silently
run a different version of itself. That branch asks `package.json`'s `name`
rather than comparing a path, because a worktree, a clone under another
directory name, and a plain `cd` all defeat a path comparison.

- [x] SC-808: package.json contains [bin, rungate] — the documented consumer interface exists at all. Two of three published commands were `bunx rungate <cmd>` against a package with no bin
- [x] SC-809: lib/cli-commands.ts contains [CLI_COMMANDS] — ONE table says what dispatches, what the manifest must ship, and what the generator may publish. Three sources disagreed and the disagreement was invisible from every direction
- [x] SC-810: test/cli-contract.test.ts contains [the script RUNS, not merely resolves] — every command is spawned for real. The issue named the vacuous version by name: asserting the table CONTAINS the text passes straight over this defect
- [x] SC-812: bin/rungate.ts contains [--project-root, process.cwd()] — a command that writes files writes into the CALLER's project. create-spec defaults its root to the package it lives in, so `bunx rungate create-spec "Title"` wrote `node_modules/rungate/specs/TITLE-SPEC.md`, printed `Created specs/TITLE-SPEC.md` and exited 0 — the documented interface existing and doing the wrong thing, which is #363 one layer in
- [x] SC-811: lib/generators/agents-md.ts contains [isHarnessItself] — the harness documents the source form and a consumer the bunx form, so neither is told to run a command that cannot work where they are

## A backtick span is not a path (#380)

`refreshAgentsMd` checked that every path mentioned in AGENTS.md resolves.
Its pattern was ``/`([^`]+\.(md|json|ts|js|tsx|yml|yaml))`/g`` — any backtick
span ending in a known extension. AGENTS.md has a **Commands** table, and
commands end in filenames, so the whole command string went to `existsSync`.

Measured on this repo before the fix:

| span | verdict | correct? |
|---|---|---|
| `bun scripts/typecheck.ts` | BROKEN | no |
| `bun scripts/test-clean-env.ts` | BROKEN | no |
| `bun test test/scaffold-conformity.test.ts` | BROKEN | no |

**Three reports, three false positives, and zero true positives.** The check
had never once validated a real reference here, and it shipped that way long
enough that every scaffold run printed the same three warnings.

That is worse than noise. A standing false positive trains readers past the
whole class, so the day it finds a real dangling pointer nobody looks. It is
also unfixable from the document's side: the span is not a path, so no edit
to AGENTS.md makes it green except deleting the Commands row — the detector
dictating the document.

### Why the true-positive count was zero, which is the uncomfortable half

D-15 capped AGENTS.md at 100 lines and moved the routing and key-file tables
into `.claude/rules/`. Every real path reference went with them. What stayed
was a Commands table of command strings. So the check was pointed at a file
that no longer names files, and the only thing it could find was the thing
it was wrong about. `referencedPaths` over the shipped AGENTS.md returns
`[]`, and the test asserts that rather than hiding it — if it stops being
zero, the file names files again and the assertion should be updated, not
deleted.

### The predicate is positive, not a blacklist

A reference is a span that is *nothing but* a path: path characters only,
ending in a known extension. A blacklist of "things that look like commands"
is the detector-narrower-than-what-it-detects shape, one unanticipated
command away from being wrong again.

**The direction this is allowed to be wrong in is toward NOT reporting.** A
real path it declines to check costs a dangling link nobody is told about —
recoverable, and the same call `.claude/rules/claiming-sc-coverage.md` makes
for the same reason.

**Deliberately not done:** extracting the path out of a command and checking
that. It would catch more — `bun scripts/typecheck.ts` really does name a
file — but a Commands table also holds `<file>` placeholders, generated
outputs and paths relative to elsewhere, and guessing which is which
reintroduces the false positives from the other end.

- [x] SC-846: lib/agents-md-refs.ts contains [isPathReference] — ONE predicate decides whether a backtick span is a file reference. `refreshAgentsMd` has two scans and they had separate patterns, so the second silently stopped covering spans the first rejected with nothing able to notice
- [x] SC-847: test/agents-md-refs.test.ts contains [a genuinely dangling path is still reported] — the positive control runs through the REAL function. "Zero broken references" is produced just as readily by a predicate narrowed to `return false`, which is the cheapest way to pass the regression case
- [x] SC-848: lib/scaffold/steps.ts contains [referencedPaths] — the audit routes both its scans through the owner rather than matching backticks inline

## The two checks that wanted the tables D-15 moved (#382, #552)

The sibling defect above, now fixed. `refreshAgentsMd` asked whether every
file in `specs/` is named in AGENTS.md, and whether `CODE-MAP.md` is. D-15
capped AGENTS.md at 100 lines and moved the specs table into
`.claude/rules/specs-routing.md` and the routing table into
`.claude/rules/docs-routing.md`. Neither check followed, so both reported on
every `--fix` run — 23 filenames and a CODE-MAP line on this repo, all
false.

**Both were unfixable from the document's side, which is what makes a
standing false positive worse than noise.** Satisfying `UNLISTED specs`
means pasting 23 filenames back into AGENTS.md, breaking the line cap D-15
moved them out to respect: the detector asking for the thing the
architecture forbids. #552 measured the consumer-facing half of that — a
consumer who adds the table by hand gets it deleted by the next
`REGENERATED: AGENTS.md`, so the warning cannot be cleared at all, and the
block it sits in also carries a real finding nobody will now read.

`lib/spec-listing.ts` is the one binding. `listingSurfaces` searches
AGENTS.md and every `.claude/rules/*.md`.

### Why the surfaces are a directory and not a filename

Naming `specs-routing.md` in the check would make it a second decider for a
question the generator already answers, which is the shape that produced
this defect. Reading the directory means a rule the generator renames stays
covered, while a spec listed in no agent-facing document at all is still
reported — the half that has to keep working. SC-1895 asserts the link
directly: every filename `generateScopedRules` writes must be a surface the
audit reads.

### `SPEC-TEMPLATE.md` is not a spec

#382 asked for this decision explicitly rather than letting it be absorbed
by whichever file a check happens to read. It is the file `create-spec`
copies to start a new spec: it governs nothing, and a reader sent to it by a
routing table learns nothing about the project. `scanSpecs` has always
excluded it from `specs-routing.md`; the audit has always included it. That
is why it appeared in the warning list as the one entry that was never going
to be listed anywhere — two deciders disagreeing, with the disagreement
showing up as a permanent warning rather than as an error.

Both sides now import `isSpecFile` from `lib/spec-listing.ts`, and the
exclusion is a named list of exact filenames rather than a pattern, so
adding to it is a visible decision.

### A third thing in the same function, deleted rather than fixed

`updateSpecsTable` was called from `write-steps.ts` immediately after the
generator rewrote AGENTS.md. It edited an EXISTING table, matched on a
header row containing `Spec`, inside an `if` with no `else` — and the
generator emits no such table, so the match never succeeded. Its action
string `UPDATED: AGENTS.md specs table from frontmatter` has never appeared
in a scaffold report, no test referenced it, and a docstring elsewhere in
the file cited it as something AGENTS.md "has already been through".

It also held a third copy of the frontmatter parse and of the what-is-a-spec
filter. Deleting it is the fix: the table it was meant to maintain is
generated into `.claude/rules/specs-routing.md`, which is where the audit
now looks.

### Where this check can still fail

The audit runs inside the rehearsal clone, where the rules have just been
regenerated, so the obvious worry is that it is now green by construction.
It is not. `specs-routing.md` is provenance-preserved (#370): a hand-edited
one is reported `PRESERVED: … generator output withheld`, and a spec added
after that edit appears in no surface. That is the live condition this check
exists for, and it is the one #549 retired a divergence over.

### A mention is not a listing, found by a row missing LOW

The first draft asked each surface `content.includes(f)`. Making
`SPEC-TEMPLATE.md` a spec again predicted 2 red and measured **1** — and
the one that did not fire was the live-tree case, the only one that matters
to the issue.

`.claude/rules/checks-must-be-able-to-fail.md:407` discusses
`specs/SPEC-TEMPLATE.md` in a paragraph about #484. A whole-document
`includes` reads that sentence as the template being listed, so the file
counted as routed by a rule that does not route it — and so would any spec
any rule file happens to name in prose. The audit would have reported
nothing while pointing readers nowhere.

That is this project's own *"search the slice, not the document"* arriving
in a function whose entire job is to decide whether a document points
somewhere. `listsFile` now requires the filename to sit on a table row or a
list item. It is deliberately permissive about which — the generator writes
rows, a consumer may write bullets — because the direction this is allowed
to be wrong in is toward reporting a spec that is in fact listed, which
costs one line in a table, rather than toward silence.

SC-1896 asserts the boundary in both directions. Narrowing a detector is the
change most likely to buy green with blindness, so it is a case rather than
a comment.

## A Repo line with no remote and nowhere to put one (#552)

Filed inside #552 as having the same cause as the audit checks above. **It
does not.** Those two read the wrong surface; this is a scan value with no
second source, and the two share only the function they land in. Measured
rather than inherited, on a git repo with no remote named `origin`:

```
scan.repoUrl                        -> ""
occurrences of "TODO: Add repo URL" ->  2
```

`detectRepoUrl` is `git remote get-url origin`, so a project whose remote
is named anything else — or which has none — gets an empty string, and the
generator wrote `<!-- TODO: Add repo URL -->` into both places it emits the
line. There was no way to answer it: `--profile=minimal` writes no
`.claude/rungate/`, so no config key exists, and editing AGENTS.md by hand
is undone by the next `REGENERATED: AGENTS.md`.

**The frontmatter is the place, because it is the one part of this file
that already survives regeneration.** `buildFrontmatter` carries forward
every simple scalar the existing block declared — that is what it is for —
so `repo:` written once by hand persists across every later run, and the
git remote stays the default wherever there is one. The TODO now names the
key, because a TODO that does not say where the answer goes is the dead end
it replaced.

Two mutations, both predicted 1 and measured 1: dropping the frontmatter
fallback, and shortening the TODO back to its old wording.

## The one section the spec guarantees survives, deleted by a run that reported success (#568)

`specs/bootstrap-data-flow/problem-statement.md` makes exactly one promise
about user content:

> **Everything is regenerable.** All harness-managed files can be rebuilt
> from scratch by re-running scaffold. **The only user-owned content that
> survives regeneration is Hard Constraints in AGENTS.md** (preserved
> between markers).

Nothing implemented it. `lib/scaffold/write-steps.ts` built the file from
the template and called `writeFileSync`. Measured on a consumer: one run
removed **37 constraint lines** — the test-container promotion sequence, a
permanently-disabled endpoint, the deploy command — and reported
`REGENERATED: AGENTS.md`, exit 0. The diff reads `M`, not `D`.

Four weeks later an agent on that project removed a flag an earlier issue
had deliberately set, because nothing in the repo said why. That is the
cost in its proper unit: not a file, a decision somebody had to make twice.

### AGENTS.md was the only rewritten file with no declared strategy

The `OWNED_FILES` table in `lib/scaffold/owned-files.ts` is #208's answer to
exactly this: a file the harness rewrites must declare HOW, and
`decideOwnedWrite` is the one binding every write routes through. AGENTS.md
— the most-rewritten file in any consumer tree — was absent from both. It
is now `section-preserving`, which is a fifth strategy rather than a
special case at the call site, because a strategy implemented at a call
site is how this one got lost.

Routing it through the writer also closed a hole in #507: a bare
`writeFileSync` FOLLOWS a symlink, so every other owned file had the
refusal and the one file every consumer has did not.

### The unit is the section, not the marker pair

The spec says "between markers", and `scripts/extract-constraints.ts` does
write between `<!-- BEGIN AUTO-EXTRACTED -->` and its `END`. On the
consumer that lost them, **most of the section was outside the markers**:
eight extracted lines between them, twenty-nine hand-written after.
Anchoring on the markers would have rescued the lines a machine can
regenerate and dropped the ones only a human holds — the most valuable
content in the file, selected against by the mechanism that was easiest to
anchor on.

So the preserved unit is the heading and everything up to the next `##`.
The markers are ordinary lines inside it, and a project that has never run
the extractor behaves identically.

### The post-condition is the check

`preserveSections` could be wrong in several ways — a missing anchor, a
heading at EOF, a template that one day grows its own Hard Constraints
section. Rather than reason about each, it compares the lines it read
against the lines it produced and reports the difference, and
`decideOwnedWrite` refuses the write when that difference is non-empty,
naming every line. A merge that silently drops something is the defect
this issue is about; a merge that names what it dropped is a decision for a
human.

### SC-139's word cap counted content the harness does not own

The golden fixture now carries a Hard Constraints section, so the
preservation is covered by the primary oracle rather than by a bespoke
test — and that immediately turned SC-139 red. Its 200-word cap is on the
prose **rungate writes**; counting a consumer's constraints against it
means a project with many non-inferable rules fails a check about the
harness's verbosity, and the cheapest way to pass is to delete
constraints. The cap now excludes the preserved section through the same
binding that preserves it, and asserts the section is present before
excluding it, so the exclusion cannot hide an empty one.

## The handoff rendered three array entries and called them the newest sessions (#572)

`scripts/update-project-state.ts` renders the most recent sessions into
PROJECT-STATE.md, the file AGENTS.md tells the next session to read first.
It selected them with:

```ts
for (const session of [...state.sessions].reverse().slice(0, 3)) {
```

That is "the last three entries of the array". It is correct exactly while
`sessions` is in append order, and nothing enforced that — not a schema,
not a test, not the writer.

**Measured:** session 48 was written to `sessions[0]` on 2026-10-17. Eight
issues merged that day and not one line of it reached PROJECT-STATE.md,
which showed sessions 47, 46 and 45 all day. Found by accident, while
appending a fourteenth item to an entry that was never being rendered.

### This is the second instance in the same function

Six lines above the loop, a comment records the first: `slice(0, 3)`
rendered the three OLDEST entries, so *"every session appended to the array
was invisible, and PROJECT-STATE.md showed ancient history to the next
session"*. The fix was `.reverse()` — which repaired the symptom and left
the defect. The renderer still had no idea which sessions were newest; it
trusted a different position.

Choosing by DATE removes position from the question, so where an entry is
written stops mattering. That is the difference between fixing an instance
and fixing the bug.

### Undated entries are ranked, not dropped

The obvious implementation excludes an entry whose `date` cannot be parsed.
That turns out to produce an EMPTY handoff for a project whose dates are
all free-form — the repo's own `sessions capped at 3` fixture is exactly
that shape — which is a worse outcome than the bug being fixed.

So an undated entry ranks below every dated one, in array order, which is
the only information left about it and is precisely what the old renderer
used for everything. Such a project renders exactly as it did before. The
entries are REPORTED by name, because being outranked by any dated entry
however old is surprising if you cannot see it.

### The run says what it rendered

`✅ rewrote PROJECT-STATE.md` was true on every run that dropped session
48, because the script had in fact rewritten the file. Success was reported
against the write rather than the output. It now names the sessions that
reached the file, so a reader who sees yesterday's date at the top of that
line knows immediately.
