# Agent Brief Template

## Problem Statement

Agent briefs (`.claude/agents/*.md`) are generated by the scaffold. Currently, the templates are hardcoded as TypeScript template literal strings inside `scripts/scaffold-project.ts` — each agent is ~80 lines of inline markdown embedded in code. To change a "Never Do" rule or add a section, you edit TypeScript, not markdown.

This creates three problems:
1. **Template changes require code changes** — editing a rule means editing scaffold-project.ts, which is a 1,400-line script
2. **Templates can't be validated by the conformity engine** — they're strings inside code, not markdown files the engine can scan
3. **No spec governs what briefs must contain** — required sections, max lines, mandatory rules are implicit in the code

The AGENTS-MD-TEMPLATE-SPEC solved this for AGENTS.md (D-3: template in `prompts/agents-md-template.md` with `${VAR}` placeholders). Agent briefs need the same treatment.

## Design Decisions

| # | Decision | Rationale |
|---|----------|-----------|
| D-1 | Agent brief templates stored as markdown files with ${VAR} placeholders | Same pattern as AGENTS.md template (SC-259). Editing a brief = editing markdown |
| D-2 | Templates live in `templates/agent-briefs/` | Separate from prompts/ (on-demand reference) and specs/ (constraints). Templates are scaffold inputs |
| D-3 | Scaffold reads template files and fills variables from project scan | Scan logic stays in scaffold-project.ts, template content is data. Same separation as AGENTS.md |
| D-4 | Each role has one template file: marcus.md, quinn.md, rook.md, serena.md, aditi.md | One file per role |
| D-5 | Shared rules in `.claude/rules/agent-principles.md` (unconditional rule) | Core Principles and Never Do load for ALL agents via project rules, not injected per-brief. `_shared.md` kept empty for backwards compat |
| D-8 | `${PROJECT_IDENTITY}` and `${SHARED_RULES}` removed from templates | Agents inherit AGENTS.md and `.claude/rules/` automatically — no duplication needed. 526→427 lines (19% reduction) |
| D-6 | Generated briefs validated by conformity engine against this spec | Required sections, max lines, mandatory rules are testable SCs |
| D-7 | Prompt routing table generated from scan, not template | The "Reference (read when needed)" section is dynamic (per-project prompts) — scaffold generates it, template doesn't include it |

## Required Sections (every agent brief must have)

1. Frontmatter (name, description, tools, model + platform-native fields below)
2. Identity line ("You are X, role description")
3. Agent-specific workflow or rules section (TDD, testing mode, scan methodology, etc.)

## Three-Tier Rule Enforcement

Rules in agent briefs are classified into three tiers. The tier determines WHERE a rule is enforced — not whether it exists (it always lives in the brief).

```mermaid
flowchart TD
    Template["Template<br/>(templates/agent-briefs/{role}.md)"]
    Template -->|scaffold| Brief["Brief<br/>(.claude/agents/{role}.md)"]
    Brief --> FM["Frontmatter<br/>tiers: reinforcement, mechanical"]

    FM --> Registry["Rule Registry<br/>(lib/rule-registry.ts)"]

    Registry --> T1["Tier 1: Identity<br/>Constraints survive burial"]
    Registry --> T2["Tier 2: Reinforcement<br/>Process rules need proximity"]
    Registry --> T3["Tier 3: Mechanical<br/>Harness enforces sequence"]

    T1 -->|"agent reads brief"| Agent["Agent Context"]
    T2 -->|"briefedAgent() injects<br/>at top of task prompt"| Agent
    T3 -->|"ship.js controls<br/>spawn sequence"| Agent

    Brief -->|"bun import"| Evals["Eval Suite<br/>getRulesForTier()"]
    Brief -->|"bun import"| Audit["Transcript Audit<br/>checkCompliance()"]
    Brief -->|"agent call"| ShipJS["ship.js<br/>loadReinforcementRules()"]
```

### Tier Definitions

| Tier | Where Enforced | What Goes Here | Why |
|------|---------------|----------------|-----|
| **Identity** | Brief (agent reads it) | Constraints, "never do X", coding philosophy | Constraints are checked against, not sequenced — survive any context position |
| **Reinforcement** | Task prompt (ship.js injects) | Process rules: "run X before/after", test discipline | Process rules collapse when buried under 600+ lines (arXiv 2608.02639) |
| **Mechanical** | Harness structure (code) | Critical sequences: TDD, test-before-commit | Agent physically can't skip — harness owns the sequence |

### Configuration

The `tiers` field in brief frontmatter maps section names to tiers:

```yaml
---
name: marcus
tiers:
  reinforcement: ['Testing Rules']
  mechanical: ['Workflow']
---
```

Sections not listed default to `identity`. The field is set in `agentMeta` in scaffold-project.ts and flows through to generated briefs.

## A brief carries one project-owned region (#655)

Every per-role surface an agent reads was regenerated from harness-wide
inputs, so a reinforcement mined from a project's own compliance history had
nowhere in that project to live. The four positions, each verified against
the source at `db66dd79`:

| Position | What it was |
|---|---|
| `lib/scaffold/owned-files.ts` | `.claude/agents/*.md` declared `regenerate`, *"Don't edit briefs"* |
| `lib/scaffold/steps.ts` | the brief write was a bare `writeFileSync(p, content)` — no `ownedStrategy`, no `decideOwnedWrite`, so the declaration above was never consulted and a bare overwrite merely coincided with it |
| `lib/generators/agent-briefs.ts` | reads only the templates, `_shared.md` and the scan; `_shared.md` resolves under `scan.harnessTemplatesDir`, so a project rule written there reaches every consumer |
| `.claude/rungate/roles.json` | `tiers.reinforcement` is a list of section NAMES (`["Discovery Rules"]`), not rule text |

`## Project Constraints` is the fourth option beyond #648's three
destinations. It works the way `AGENTS.md`'s `## Hard Constraints` does
(#568) and **through the same merge**, which is the design decision worth
stating: `preserveSections` takes a `SectionSpec` and the two files supply
different vocabularies. Two copies of the merge with different constants
would be two deciders answering one question, and a mutation of either would
leave the other holding every case up.

The section is **opt-in** and no template emits it. A generated section
would take `preserveSections`' own-section branch and refuse every
re-scaffold on every consumer that had written one, which is the opposite of
the promise.

The hill-climb **prefers** the region and does not create it. Creating it
would make `NO_SECTION` unreachable and silently change every receipt #646
made reportable; a brief with none of the four headings still reaches that
state.

#### The cheapest wrong fix, named, applied and measured

**Named:** call the preservation at `generateAgentBriefsStep`'s write site —
a literal `"section-preserving"` and a literal `BRIEF_CONSTRAINTS_SECTION`
— and leave the `OWNED_FILES` row and `.claude/rules/harness-managed.md`
both saying `regenerate` / *"Don't edit briefs"*. One import, two literals.

It is the 5pm repair and it **works**: `bun run typecheck` reports 0 errors
and **46 of 48 pass**. Every behavioural case is green — the marker
survives, the merge is idempotent, the refusal fires and names its lines,
the reinforcement lands in the region and survives a re-scaffold. The three
reconciliation cases in `test/scaffold-ownership.test.ts` are green too,
*because `OWNED_FILES` was never touched*, so the doc and the declaration
still agree with each other about the wrong thing.

What ships is a brief that preserves edits while every surface a human or an
agent reads to decide whether to edit one says not to — the declared
contract and the behaviour disagreeing, with the documentation as the half
that is wrong. That is the state the bare `writeFileSync` had already left
this row in, and it is why criterion 3 is load-bearing rather than
documentation hygiene.

**The two cases that survive it are SC-2131 and SC-2139, and they are the
only protection.** SC-2131 because reverting the row leaves one
section-preserving entry where the declaration now requires more than one
that declares its section; SC-2139 because it reads the write loop and
refuses a strategy literal there. Neither is a behavioural case and neither
could be — a repair that is behaviourally correct cannot be caught by
watching behaviour.

None of the seven mutations is left in the tree; all were run and reverted,
and `lib/scaffold/steps.ts`, `lib/scaffold/owned-files.ts`,
`lib/agents-md-sections.ts`, `lib/compliance-report.ts`,
`.claude/rules/harness-managed.md` and `test/brief-project-region.test.ts`
were confirmed byte-identical to the measured source afterwards by
`shasum -a 256 -c`, with the baseline re-measured at 48 pass / 0 fail.

### What #655 did NOT do

- **The region is not created for a consumer.** A project opts in by writing
  the heading, exactly as it does for `AGENTS.md`'s `## Hard Constraints`.
  Making the hill-climb write the heading when it is absent would make
  `NO_SECTION` unreachable and change every receipt #646 shipped, so it is a
  decision for #648 with that cost stated rather than a side effect here.
- **The `COMMIT` default is unchanged.** Which destination the shipped loop
  uses is #648's first criterion and has to move
  `scripts/persist-compliance.ts`'s re-grade step with it.
- **`roles.json` still carries section names, not rule text.** Nothing here
  needed it: the region is in the brief, which is where a rule an agent
  reads has to be.

## Cautions

- Template files are scaffold INPUTS, not outputs — don't regenerate them on re-scaffold
- The `_shared.md` partial is a convention, not a framework — simple file inclusion, not a template engine
- Keep templates readable as standalone markdown — someone should be able to read `templates/agent-briefs/marcus.md` and understand what the brief will look like
- Don't over-engineer variable substitution — `${VAR}` string replacement is sufficient, no need for Handlebars/Mustache
