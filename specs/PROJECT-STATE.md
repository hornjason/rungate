# Project State

## What this file was, and why that was a defect (#579)

Until 2026-10-17 this document was a **rendered `PROJECT-STATE.md` snapshot
from 2026-09-22 with spec frontmatter pasted on top**. Its body was the
generator's own output: a "Current phase" line, a "Next priorities" list, and
`| Status | SC | What |` tables citing criteria it did not declare. It stated
`Suite: 984 tests`; the suite was at 11,961. Every priority in its list had
shipped weeks earlier.

`.claude/rules/specs-routing.md` — the table every agent is told to consult
before changing an area — presented it as the governing spec for project state
management. An agent that followed the routing table before touching
`scripts/update-project-state.ts` arrived here and got **no requirements at
all**, because it was never a requirements document.

That is worse than a gap in the table. A gap is visible; this was not. The
reader believes they have arrived.

It is also why the project-state criteria lived somewhere else: SC-296, SC-297,
SC-298 and SC-308 sat in `AGENTS-MD-TEMPLATE-SPEC.md`, whose `governs` is
"AGENTS.md template structure", and #572's SC-1960..SC-1963 went there for
consistency with the ones already present rather than because it was the right
home. The right home did not exist. It does now, and they have moved here.

## The contract

### `project-state.json` is the source; `PROJECT-STATE.md` is a rendering

`PROJECT-STATE.md` is generated by `scripts/update-project-state.ts` and must
never be hand-edited — an edit survives exactly until the next run. Anything
that has to persist belongs in `project-state.json`.

### Both files, and `SUCCESS.md`, are DA-owned

An agent running in a worktree must never write them (#296 — the issue, not
the criterion). They are a single shared state document, so four parallel
worktrees each updating their own copy produce four conflicting versions, and
the collection guard refuses the whole run when a worktree reports a file no
sub-issue claimed. On 2026-10-11 that cost run `wf_0b15a933-b2b` four
worktrees and 2,565 lines of validated work. An agent that believes one of
these files needs updating says so in its findings as prose, and the DA writes
it.

### Status is scanned, not typed

Phase and criterion status come from scanning `specs/` frontmatter and
checkbox state, not from anything a human maintains by hand in
`project-state.json`. A status table a human has to remember to update is a
status table that reports the day somebody last remembered.

### The handoff selects by date, and reports what it selected

The session handoff renders the newest sessions by **date**, never by array
position (#572). The DA writes new sessions to the front of the array and the
old renderer read from the back, so a whole day of work never reached the
handoff while `✅ rewrote PROJECT-STATE.md` was printed truthfully on every
run — success was reported against the write rather than against the output.

An entry whose date cannot be parsed is **ranked below every dated one and
named**, not dropped: excluding it produces an empty handoff for a project
whose dates are all free-form, which is worse than the bug being fixed.

The run names the sessions that reached the file. `✅ rewrote` is a statement
about a write; a reader needs a statement about the output.

### The rendering is bounded

`PROJECT-STATE.md` is a context-loaded file read at the start of every
session, so it is capped. Growth is paid for out of every agent's context
budget on every run.
